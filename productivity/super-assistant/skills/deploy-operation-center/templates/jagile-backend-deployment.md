## 1. 部署前锁定目标

每次部署必须记录八项信息：

| 字段 | 说明 |
|---|---|
| 应用 | 精确应用名 |
| 环境 | 测试、预发或生产 |
| 分组 | 第几套环境或具体分组名 |
| IP | 目标实例地址 |
| 构建参数 | profile、环境参数和构建命令 |
| 制品 | 版本号或制品标识 |
| 提交 | Git commit SHA |
| 构建人 | 制品实际构建账号 |

目标优先从需求部署文档、现有部署记录、应用消费者配置和用户明确说明中确定。多个实例都可能正确时，不猜测；共享测试实例覆盖前向用户确认。

## 2. 构建与制品

在行云选择与已验证本地构建一致的开发分支和构建参数。构建完成后核对：

- 制品对应的提交号就是已测试提交。
- 构建人、时间和版本与本轮操作一致。
- 不复用来源不明或由其他需求构建的同名制品。

如果用户指定“当前制品的构建人”，将它作为筛选制品的硬条件，而不是备注。

## 3. 实例部署

按项目部署文档选择“指定 IP 部署”或对应部署入口，确认分组和实例后再提交。部署过程中观察：

- 下载制品和启动是否成功。
- 实例运行状态是否稳定。
- 运行时版本、提交号和制品是否匹配。
- 应用日志是否出现 Spring 启动失败、配置占位符缺失或端口冲突。

需要日志时调用 `$log-operation-center`。不要只看行云界面的“运行中”就认定应用业务可用。

## 4. 配置优先级与生效方式

排查配置时按三层对照：

1. 源码 profile 中的配置。
2. 行云应用或分组级配置覆盖。
3. 实例内最终运行时配置。

实例真正读取的是第三层。源码正确但行云分组覆盖错误时，重构制品并不能解决问题。

修改行云分组配置后，优先使用同一正确制品重新部署到目标实例，使配置在部署阶段重新注入。单独重启进程可能继续使用旧运行时配置，不能假定一定生效。

### JSF 占位符缺失时的成组完整性检查

遇到 `Could not resolve placeholder '${jsf.*}'`、JSF consumer Bean 创建失败，或启动日志在补完一个 timeout 后又暴露 alias 缺失时，按配置块成组排查，不要按异常逐个 key 反复部署：

1. **锁定值来源。** 记录当前实例的制品、Git 提交、构建 profile 和运行配置版本。只把“该制品对应提交下、该 profile 的源码配置”作为期望值来源；其他测试分组或稳定环境只能用于旁证，不能直接复制。
2. **收集完整引用集。** 从失败 Bean 对应的 Spring XML、Java `@Value` 或配置绑定类出发，收集同一组 JSF consumer/provider 引用的全部 key，至少覆盖 `alias`、`timeout` 及同一节点的其他占位符。Spring 可能按 Bean 创建顺序延迟解析，当前日志只会暴露最先遇到的缺失项。
3. **计算运行时差集。** 对照实例最终配置，列出“源码引用且 profile 有值、运行时文件缺失或值不同”的全部 key。检查行云托管文件是否用旧快照覆盖了制品内配置；不要因源码文件正确就跳过实例核验。
4. **一次性最小修复。** 只修改目标应用、环境和分组中已证实漂移的 key，并保持原文件换行、注释和属性语法。保存后重新打开托管文件，逐项搜索并确认每个 key 恰好存在且值正确，避免编辑器把新增属性拼接到注释或上一行。
5. **用同一制品重新注入。** 记录新配置版本，使用已经核准的同一制品滚动部署；配置问题未涉及代码时不要无意义重构制品。部署后再次核对实例最终配置，而不是只看行云保存成功提示。
6. **按启动链验收。** 当前批次的控制台或业务日志中不得再有未解析占位符、`BeanCreationException` 或 `Exception in thread "main"`；容器启动日志必须在超时前出现 `start success` 或等价成功标志；实例版本应切到新配置版本，JSF Provider 数量、alias 和 IP 应达到预期。

如果修复后的首轮部署仍出现同一配置区域的新缺失 key，停止继续“一键一部署”，回到第 2 步扩大到完整配置块重新计算差集。Log4j 配置警告、探针或后台线程存活不能覆盖 Spring 主容器失败的事实，应根据异常因果链和 JSF 实际注册结果区分阻断项与非阻断告警。

## 5. JSF 提供者与消费者

JSF 提供者部署后必须在注册中心核对：

- 预期接口数是否全部在线。
- 别名、分组、IP、端口和环境是否正确。
- 离线接口对应的 Spring Bean 是否完成初始化。

“只上线 1 个接口”不一定是注册中心故障。若 Spring 在创建后续 Bean 时因占位符、依赖或类加载异常中止，进程可能存在但只有启动中较早注册的接口在线，应结合启动日志确认。

消费者无请求打入提供者时依次确认：

1. 消费者实例实际读取的 JSF alias。
2. 注册中心该 alias 下是否存在目标提供者。
3. 消费者部署分组与提供者环境是否配套。
4. 调用是否在消费者本地校验、路由或代理层提前失败。

例如 portal 和 manager 分别部署在多套测试环境时，以 portal 运行时的 manager alias 和注册中心提供者为准，不能仅根据 IP 猜测调用目标。

## 6. JSF 上线失败且 Provider 为 0 的诊断闭环

遇到以下组合时，不要把问题直接归因于注册中心：

- 行云实例的应用或进程状态正常，但 J 标灰色、JSF 接口数为 `0`。
- Java 进程存在，JSF 上线动作却提示未注册成功，例如错误码 `1002705000`。
- 变更记录中的“JSF上线”任务显示“完成”，实际 Provider 数仍为 `0`。

“任务完成”只表示平台动作执行结束，不表示业务效果成功。按以下顺序闭环：

1. **锁定当前启动批次。** 记录部署版本、制品、变更任务、启动时间和当前 PID。共享环境可能有其他人同时停止、启动或灰度部署；每次操作前刷新状态和变更记录，避免依据旧版本继续判断。
2. **读取真正承载 Spring 异常的日志。** 控制台日志可能只有配置加载或 RASP/JDK 警告，业务启动异常常写入 `/export/logs/<应用>_detail.log` 等应用日志。按当前启动时间筛选，避免把上一 PID 的异常当成当前结果。
3. **判断 JVM 存活是否是假健康。** 若启动日志出现 `BeanCreationException`、`TypeMismatchException`、未解析的 `${...}`、`ApplicationContext` 初始化取消或销毁，即使 Java 进程仍在也按启动失败处理。JSF 消费者、配置中心或监控后台线程可能让 JVM 在 Spring 主容器退出后继续存活。
4. **从异常字段反查三层配置。** 对 `@Value("${key}")`、XML 占位符或绑定失败的 key，逐项对比源码 profile、行云分组配置和实例最终配置。源码中存在 key 不能证明实例已加载；行云托管文件可能以旧内容覆盖制品内正确配置。
5. **修复最小配置并重新注入。** 只修改已证实缺失或错误的目标分组配置，保存后用同一已确认制品重新部署。核对新配置版本，并在实例内确认最终文件含有期望值。
6. **等待 Provider 真正导出。** 先确认新启动日志无致命 Spring 异常，并出现类似 `JSF export provider ... after spring context refreshed` 的记录；统计导出的 Provider、alias 和目标 IP。不要在 Provider 尚未创建时抢先执行 JSF 上线。
7. **执行上线并验证效果。** Provider 已导出后再执行 JSF 上线。最终以注册中心或行云实例页的 Provider 实际数量、alias、IP 和在线状态为准；任务状态、绿色进程图标或一次无报错点击都不能替代这一步。

若 Provider 已按预期导出但平台仍显示 `0`，再到 JSF 管理端查询该 IP 的实例详情：

- Provider 数仍为 `0`：继续检查导出阻塞、注册参数、alias、注册中心地址和运行时配置。
- Provider 数正常但状态为死亡或下线：检查容器重启期间的行云流程动作，必要时联系行云部署支持。
- Provider 数和状态均正常但行云未刷新：优先判断为平台状态同步问题，不要反复重启已健康的业务进程。

一个常见时序陷阱是：配置修复后的部署尚未完成 Spring 刷新，就执行了 JSF 上线，因此第一次仍报 Provider 为 `0`；稍后日志已经完成 Provider 导出，但平台不会自动把失败动作改成成功。此时应基于最新版本和启动时间重新核验，再执行上线，不能沿用第一次动作的结论。

## 7. `No alive provider` 的 alias 错配闭环

`[JSF-22010] No alive provider` 的 key 是“接口 + alias”，不能只按接口判断。按以下顺序处理：

1. **确认错误来源。** 在报错实例的最终运行时配置和当前、轮转日志中查找完整接口与 alias。若目标应用只声明该接口为 provider，且自身配置和历史日志均无该错误 alias，则把报错归到外部消费方或上线校验，不要误改当前应用的 consumer 配置。
2. **核对真实二元组。** 对比消费端最终 alias、注册中心该接口下的实际 alias、IP、端口和 PID。源码 profile 只能作为线索，不能替代行云托管配置和实例最终文件。
3. **优先修消费端。** 已定位消费方时，把消费 alias 改为目标环境现有 provider alias，并重新部署消费方。不要为了单个错误调用方覆盖 provider 主 alias，否则会切断其他正常调用方。
4. **必要时做环境级兼容。** 消费方暂时无法修改且测试环境必须立即恢复时，在目标分组中保留原 provider，并为同一接口和实现增加不同 id、错误方所需 alias 的第二 provider。把兼容限定在目标测试分组；避免把临时 alias 写进生产通用配置。
5. **重新注入并验证。** 修改行云配置后用同一制品重部署。预期 Provider 总数增加 `1`；在实例日志中提取该接口的唯一注册记录，确认主 alias 和兼容 alias 同时指向当前 IP、端口和 PID。只看到进程或单条导出日志不算完成。
6. **验证消费效果和回退。** 能定位消费方时重新触发最小只读调用并检查其新日志不再出现同一 key。若兼容注册无效或产生冲突，删除第二 provider 或对应托管配置，再用原制品重部署恢复。

行云 application 类型应用若使用分组托管文件覆盖 Spring 配置，目标路径通常写为 `/home/export/App/conf/spring/<文件名>`，部署后映射到实例运行目录。新增整份 XML 会形成源码快照漂移风险；使用前保存原内容，后续优先把长期方案收敛到明确的消费端配置或可维护的源码方案。

## 8. 验证与回退边界

部署后至少验证：

- 实例状态与运行时制品信息。
- 实例最终配置中的修复项和配置版本。
- Spring 启动完成标志，无未处理启动异常。
- JSF Provider 导出记录，以及注册中心中预期接口的在线数量、alias 和 IP。
- 一个最小只读业务请求能够到达目标实例。

未经用户授权不要在共享测试环境切换其他人的制品。部署失败时可以用已经确认的上一制品恢复当前实例，但回退属于状态变更，目标版本必须明确并在结果中说明。
