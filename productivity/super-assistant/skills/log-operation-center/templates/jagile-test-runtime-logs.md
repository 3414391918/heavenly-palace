# 测试环境行云实例日志

## 1. 适用场景

优先使用行云实例日志和终端的情况：

- 应用刚部署或重启，需要确认启动是否完成。
- Spring 容器启动失败、端口异常或配置占位符缺失。
- JSF 接口只上线一部分或全部未上线。
- 源码配置正确，但实例行为仍像旧配置。
- 用户已给出明确应用、分组、IP，希望直接观察该实例。

已经发生的业务请求需要跨实例、按 traceId 或时间范围检索时，仍优先使用 Digger 历史日志。需要边操作边观察业务明细时，可使用 Digger 实时日志。

## 2. 锁定正确实例

进入日志前记录：应用、环境、分组、IP、制品版本、Git 提交、构建人和部署时间。页面当前显示的信息比历史文档中的固定路径或截图更权威。

如果同一应用存在多套测试环境，不能只按应用名选择。先根据调用方运行时 alias、部署文档或用户说明确认分组，再核对实例 IP 和制品。

## 3. 入口选择

在行云应用管理中进入目标分组和实例列表：

- “日志”：观察应用实时输出和请求日志。
- “Digger”：跳转到可按关键字、时间和实例筛选的日志检索。
- “终端”：检查 `/export/logs` 等实际日志文件以及实例最终配置。

行云入口通常为 `http://jagile.jd.com/jdosCD/lstest/apps`。如果当前页面路由不同，从行云导航进入“应用管理 → 测试环境 → 分组 → 实例列表”，不要依赖旧 URL 硬跳。

## 4. 启动失败排查

先读取最新启动日志，再定位第一条根因，不从最后一条级联异常开始猜测。实例终端可按实际目录使用类似命令：

```bash
tail -n 200 /export/logs/console.log
grep -n 'Exception in thread\|BeanCreationException\|Caused by' /export/logs/console.log | tail -80
```

服务器未必安装 `rg`，终端内可使用 `grep`。本地源码搜索仍优先使用 `rg` 或 CodeGraph。

常见判断顺序：

1. 是否下载并启动了正确制品。
2. JDK、端口和启动参数是否正确。
3. Spring profile 和配置文件是否加载。
4. 第一条 `Caused by` 是否为占位符、Bean、类加载或远程依赖问题。
5. 启动失败前是否已有少量 JSF 接口注册，从而出现“只在线 1 个接口”。

JSF 数量异常只是结果，不能直接认定注册中心有问题。

## 5. 配置未生效排查

按三层比对：源码 profile、行云应用/分组配置、实例最终运行时配置。最终以实例文件和启动参数为准。

示例：

```bash
grep -n '<配置关键字>' /home/export/App/conf/*.properties
```

路径必须根据当前应用实际目录调整。确认行云配置变更后，通常需要用同一正确制品重新部署，使配置重新注入；仅重启不一定刷新配置。

## 6. 业务请求实时观察

在发起请求前先打开目标实例日志，记录观察起始时间。请求完成后保留：

- 请求地址或 JSF 接口、请求时间和关键参数。
- 响应参数或前端错误。
- 命中的实例 IP、日志文件和第一条异常。
- traceId；一旦日志中出现 traceId，转到 Digger 用完整 traceId 查询全链路。

日志中可能包含 pin、手机号、令牌或其他敏感信息。输出报告时只保留排障必需字段，不复制密码、Cookie、Authorization 或完整令牌。

## 7. 完成标准

结论必须能回答：请求是否到达正确实例、实例运行的是否为目标制品、配置是否为预期值、第一条直接异常是什么、JSF 或业务调用恢复后如何验证。只有现象没有这些证据时，继续查询，不宣称已经定位。
