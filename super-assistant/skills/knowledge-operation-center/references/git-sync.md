# Git 管理知识库与多机协作

知识保存在每台机器的本地 `knowledgebases`；Git 远端保存已提交并推送的版本。安装 Obsidian 或登录账号本身不会把 vault 上传到云端。本方案使用 Git，不要求购买 Obsidian Sync 或安装社区插件。

## 内容与可见性

同步 Markdown、来源清单、附件（按必要范围）、模板、`.base`、通用 `.obsidian` 设置和 Skill。应用、安装包、窗口布局、缓存、回收站、凭据和本机绝对路径不进入提交。`.gitignore` 不会移除已跟踪文件，发现已跟踪二进制先报告，勿擅自重写历史。

导入时检查来源的披露范围和目标远端可见性。公司内部来源中的“公开”可能仅指组织内公开，不等于可向互联网公开。公共 GitHub 仓库中的内部知识先本地整理；对外同步前需取得明确的披露授权或选择符合资料权限的私有存储，不能把“用 Git 管理”推断为允许公开披露。只需本地管理时不必等待远端决策。

## 每台机器的日常流程

1. 工作前 `git status --short`。工作区干净时 `git fetch`、`git pull --ff-only`；有未提交修改先保留并检查，不自动 stash/reset。
2. 打开本机 vault，运行探测脚本确认路径。修改知识后检查属性、来源、链接并追加操作日志。
3. 按本次范围 `git add -- <明确路径>`，检查 `git diff --cached --stat`、`git diff --cached --check` 及完整差异，确认无安装包、凭据或越界内容。
4. 用户已授权提交/同步且可见性适合时，使用普通 `git commit` 与 `git push`。不要 `git add .` 混入其他任务，也不要强推。
5. 换机器前完成允许的同步。另一台机器先拉取再编辑；未推送的本地修改不会自动出现在别的机器。

## 并发冲突

推送被拒或快进失败时先 fetch 查看双方改动。正文保留双方事实与来源，按上下文合并；无法裁定的内容保留为待审查分歧。追加日志保留双方记录。`.base` 与通用设置人工核对有效格式，用户专属 workspace 已忽略。验证后正常提交合并结果；不要整篇使用 ours/theirs、reset --hard 或重写历史来消除冲突。

Git 的提交号、文件历史、diff、blame 提供版本追溯；笔记里的来源 URL / 稳定 ID 提供证据追溯；导航、标签、属性和双链提供检索。不需要向量数据库。
