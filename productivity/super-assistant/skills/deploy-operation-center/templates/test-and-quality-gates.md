# 单元测试与质量门禁

## 1. 测试分层

按风险从小到大执行：

1. 新增或修改逻辑的单元测试。
2. 发生冲突的模块测试。
3. 公共包及直接消费方测试。
4. 项目已有的全量单测或构建门禁。

前端至少执行受影响组件或工具函数测试以及目标环境构建。需要 NVM 时先读取 `.nvmrc`、`package.json` engines 和项目部署文档，不随意升级 Node 或锁文件。

## 2. 真实结果

报告必须记录完整命令和真实结果：执行数、失败数、错误数、跳过数。Java 项目优先核对 Surefire/Failsafe 报告；前端核对测试运行器汇总和构建退出码。

以下情况不能报告“单测通过”：

- 0 个测试被执行，但项目实际存在相关测试。
- Maven 配置忽略了测试失败。
- 只执行了编译，没有执行测试。
- 命令超时或日志被截断，未看到最终结果。
- 仅凭 `BUILD SUCCESS`，未核对测试汇总。

## 3. 合并后的回归

合入 `origin/master` 后必须重新执行：

- 冲突文件所在模块的测试。
- 需求新增或修改逻辑的测试。
- 公共 API、DTO、枚举发生变化时的消费方编译和测试。
- 项目专属合并指南规定的全部门禁。

若出现与需求无关且在 master 已存在的基线失败，先用 master 或历史报告证明它是基线问题。不要在当前需求中顺手修复；把证据和影响告诉用户。

## 4. 文件完整性

测试通过后仍要检查代码和测试文件是否被意外删除：

```bash
git diff --diff-filter=D --name-status origin/master...HEAD
git ls-tree -r --name-only origin/master
git ls-tree -r --name-only HEAD
```

重点比较 `src/test`、`test`、`tests`、`__tests__` 以及 `*Test.java`、`*.test.*`、`*.spec.*`。每个删除都必须能由需求直接解释。

## 5. 部署前检查点

部署前确认：

- 代码、公共包和消费方都已推送到预期远端分支。
- 构建使用的提交号与已测试提交一致。
- 构建参数和环境 profile 正确。
- 用户要求的人工检查点已经完成。

用户明确表示后端由其部署时，代码和单测完成后先通知用户，等待其确认部署成功再继续联调或链路测试。
