# 知识操作中心

用 Obsidian 保存和维护研发知识。人负责确认事实与决策，AI 负责提炼、查重、关联、生成草案和执行已获授权的操作。

这是一个独立 Skill：知识管理流程在本文件，CLI、Markdown 和 Bases 用法按需读取下列参考资料，无需加载其他 Obsidian Skill。

## 运行前提与定位

- Obsidian 由用户自行安装；Skill 不要求固定的应用安装目录。首次使用按 [初始化说明](references/initialization.md) 连接知识库、启用 CLI 并核验路径。配套脚本使用 Bash，Windows 使用 Git Bash。
- 打开目标 vault 并启用 CLI 后，运行 `scripts/detect_obsidian.sh`。只有返回真实预期路径与 `VAULT_READY=yes` 才能继续。
- 脚本默认操作本 Skill 内的 `knowledgebases`，可用 `OBSIDIAN_VAULT_PATH` 显式指定其他库；CLI 位置通过 `OBSIDIAN_CLI` 或 `OBSIDIAN_INSTALL_DIR` 指定。机器路径留在本地环境，不写入同步配置。
- 通用命令使用 `bash scripts/obsidian.sh <命令> ...`，它先核对 Vault 路径；不要仅依赖最近聚焦的库。执行前用 `help` 确认命令，笔记定位用完整 `path=`。
- 所有相对脚本路径以本 Skill 目录为基准。Git 多机使用方式和远端可见性按 [Git 同步规范](references/git-sync.md)；源资料能否公开须依据实际授权判断。

## 操作边界

1. **通过 CLI 操作 vault。** 本 Skill 用 CLI 统一定位、校验和记录操作；本地临时正文文件可经文件工具读写。Obsidian 本身支持感知外部文件变化，CLI 是本工作流的操作约定，不能声称外部编辑必然导致索引失效。
2. **知识正文先形成待审草案。** 新笔记、重构和正式文档的增量更新先进入 `0-临时文件/待审查/`；批准后才合并正式文档或移动归位。操作日志和经授权的状态维护按各工作流执行。
3. **按已有授权执行。** 用户明确要求记录或更新，已授权生成相应草案，无需再问一次是否记录；草案审查通过与移动归位是后续独立动作。纯查询不隐含写入授权，长对话结束可询问一次是否沉淀。
4. **保留知识文档。** 废弃内容标为 `已归档` 并移入 `4-历史归档/`。删除仅用于已合并的 AI 临时补丁，或经授权移动且已核验完整目标副本后的源文件清理。
5. **保留事实分歧。** 冲突处保留两种表述和证据，注明取代关系或待裁决事项；不把 AI 建议写成已确认决策。
6. **区分笔记与视图操作。** 日常知识管理中 `.base` 只读；用户明确要求创建或修改 Bases 时，按指定范围编辑并验证。`3-静态资源/` 原始资料、`5-系统模板/` 和 `6-绘图文件/` 在知识整理流程中只读。
7. **初始化例外。** 用户要求初始化或测试本 Skill 时，可创建缺失目录、模板、Base、来源清单和通用配置；保留用户已有内容。测试只清理本次创建的测试数据，不改变真实知识的审查状态。
8. **标明证据状态。** 外部来源未验证时，在正文顶部加警告 callout。来源追溯只填写实际获得的讨论、文档或证据；不虚构提交号、日志地址或测试结果。

## 知识库约定

下面是本工作流的七个目录。先检查现有 vault；用户已有明确目录约定时沿用其映射，不自行搬迁或初始化整库。

| 目录 | 用途与操作范围 |
|------|----------------|
| `0-临时文件/` | 原始随笔；AI 草案写入其下 `待审查/`，其余原始内容只读 |
| `1-动态项目/` | 活跃项目、需求和待办；确认归位后移入 |
| `2-长期领域/` | 可长期复用的领域知识；确认归位后移入 |
| `3-静态资源/` | 参考资料和附件原始源，只读 |
| `4-历史归档/` | 完成或废弃文档，按归档指令移入 |
| `5-系统模板/` | 模板与字段选项，只读 |
| `6-绘图文件/` | 绘图文件，只读 |

目录负责物理分类，文档属性负责筛选，`[[wikilink]]` 负责关联。`.base` 保存视图规则，不是元数据缓存；关系图谱由 Obsidian 的 Graph view 展示。

随附 `知识库总览.base` 提供全库、待审查、已确认和最近修改视图，按来源字段筛选知识条目；其他业务视图按需增加。先检查实际存在的视图；缺少总览时可用 `search` 查询，不要求为一次查询新建视图。CLI `base:query` 用于已有视图，动态关键词、标签和目录条件用 CLI `search`。

## 内容整理原则

1. **提炼信息。** 优先保存综合结论、可复用事实和决策。能否独立解释、是否有独立关联、内容是否足以成页，决定新建页面还是并入已有小节；避免把单个小来源原样复制成另一页。
2. **按审查状态使用。** 优先引用 `已确认` 页，`待审查` 仅作为草稿提示；历史确认不代表当前代码或环境仍然一致，涉及当前状态或出现冲突时按证据核验。
3. **先找候选再读正文。** 用 Base 视图或 `search` 缩小范围，只读相关页，不为判断相关性通读整库。
4. **先查重再决定写法。** 阅读最相似的现有页，通常最多先读两篇；没有候选时可直接进入新建。已有页完整且无新增信息则不写；有补充或纠错则更新；多页互补则提出合并；无法融入已有页才新建。
5. **一个主题保留一份正式文档和至多一份待审补丁。** 避免 `-v2`、`-完善版`、`-合并版`；同一原文的新增修改合入现有补丁。
6. **保存决策理由与反转条件。** 说明为什么这样决定，以及何种条件下应重新考虑。
7. **查询结论可回填。** 新形成的对比、根因或决策具有复用价值时，按已有授权写入待审查区；没有写入授权时先询问。

## 笔记脚本与格式约定

| 脚本 | 用途 |
|------|------|
| [create_note.sh](scripts/create_note.sh) | 新建正文并逐项设置属性；目标已存在时退出码 3，转更新流程 |
| [merge_note.sh](scripts/merge_note.sh) | 整篇更新并补回属性；原文不存在时退出码 3，转新建流程 |
| [write_note.sh](scripts/write_note.sh) | 所有正文经本地临时文件写入与 SHA-256 回读校验；`--mkdir` 补建父目录 |
| [obsidian.sh](scripts/obsidian.sh) / [detect_obsidian.sh](scripts/detect_obsidian.sh) | 安全定位 CLI 与目标库，执行通用命令 |

- 参数、退出码和限制先看脚本 `--help`。三个脚本保持在同一目录；create/merge 的所有正文均使用 write_note，保留中文、引号、字面量反斜杠及尾部空行。
- 正文源传本地文件或 `-`（stdin）。vault 中的正文先用 CLI `read path="..."` 导出到本地临时文件；不要把 vault 相对路径误当本地正文文件。
- 脚本采用“正文 + 独立属性参数”输入，正文不携带 YAML frontmatter；先写正文再逐项 `property:set`。Markdown 参考中的 YAML 示例展示的是最终文档格式。
- 创建知识草案放入待审查区；配套脚本写入时不打开笔记窗口，直接用 CLI create 时带 `silent`；动态项目归位后可用 `1-动态项目/YYYY-MM-DD 项目名/`。
- CLI `templates` 列出实际模板，`template:read name="模板名" resolve` 读取正文与字段选项。业务枚举以实际模板为准，不复制硬编码。
- 脚本通过 `cli_env.sh` 从目标 vault 目录执行并校验路径；直接调用官方 CLI 时，`vault=<名称或ID>` 必须是第一个参数，并自行核验目标。
- 每次改文档同步更新自定义属性 `修改时间`。手动覆盖前保留全部属性，覆盖后补回；模板占位串必须替换为真实值。
- 脚本回读校验通过后，无需机械重复同一次正文检查；属性或输出异常时按 [gotchas.md](references/gotchas.md) 定位。

示例（在本 Skill 目录执行，`body.md` 是已准备的本地正文文件）：

```bash
bash scripts/create_note.sh "0-临时文件/待审查/鉴权费用融合.md" body.md \
  "审查状态=待审查" "来源追溯=鉴权费用融合方案讨论" \
  "aliases=鉴权费用融合" "tags=开发文档,鉴权,计费"
```

## 工作流

### 1. 沉淀研发成果

网站批量导入先按 [来源导入规范](references/source-import.md) 枚举并建立来源清单，再执行本流程。

1. 确认记录范围与已有授权，按内容整理原则提炼并查重。
2. 使正文脱离当前对话也能读懂，去掉“上面提到的”等指代；明确已确认事实、待确认方案及来源。
3. 需要结构时读取实际模板，使用 Markdown 参考编写正文；可并入已有文档时转增量更新。
4. 用 create_note 创建草案，设 `审查状态=待审查`，补充来源、标签、别名和时间。
5. 按日志规范追加“新建”记录，告知草案路径及需要审查的内容。

### 2. 查询历史知识

1. 将问题转为关键词、标签、目录或属性条件；用已有 Base 视图或 `search` 获取候选清单。
2. 用 `read` 读取命中页，必要时用 `search:context` 查看匹配片段，用 `backlinks` 与 `links` 追踪关联。
3. 优先综合已确认文档，区分草稿、陈旧内容及矛盾，回答附对应文档链接。
4. 新的综合结论需要保存时，按内容整理原则 7 处理。

### 3. 增量更新正式文档

1. 在待审查区生成 `[原标题]-补丁-YYYY-MM-DD`；有同一目标的待审补丁时继续更新它。设 `补丁目标` 为指向原文的 wikilink，状态为待审查。
2. 顶部 callout 说明改动、理由和冲突；正文给出完整拟合并版本，保留原文仍成立的事实。
3. 批量更新先给受影响页面与原因清单；范围已经获授权时按范围生成补丁，否则先明确范围。
4. 审查通过后，整篇更新用 merge_note；局部补充可用 `append`，先确认原文没有重复内容。保留并补回全部原有属性，更新修改时间。
5. 验证合并结果后清理补丁，追加“更新”日志。手动覆盖注意 `overwrite` 会丢失未补回的属性。

### 4. 审查后归位

1. 查询已经确认、仍在待审查区的文档。状态改成已确认本身不触发移动，需有归位指令。
2. 给出目标目录和理由；已有明确归位范围与目标时直接执行，未明确时先完成提案。
3. 用 CLI `move` 移动。目标目录缺失或命令失败时参照 gotchas 的文件移动小节；复制后清理源文件必须先核验目标正文、属性和引用完整。
4. 用 `unresolved` 检查断链，追加“移动”日志。用户已手动移动过文件时，先重新定位，避免沿用旧路径。

### 5. 巡检与整理

1. 按用户范围检查长期待审草稿、已完成但未归档的项目、矛盾和过期内容。
2. 用 `orphans` 查孤立页、`deadends` 查没有出链的页、`unresolved` 查未解析链接；缺少出链不直接等同于失效链接。
3. 输出报告与修订建议；获授权的正文或补链修改生成待审草案，不直接改变已确认正文。
4. 依照 frontmatter-spec 校验属性和日志格式。日志日常只追加；历史格式整理先给修订提案，明确授权后保留原有记录再处理。
5. 需要标为 `需重构`、补充关联或归档的页面，按既有授权处理并记录相应日志。

### 6. 综合与重构

1. 找出主题重叠、同一演化过程的前后阶段、信息互补或缺少综合结论的页面。
2. 读取相关页，按主题组织成连贯草案，解释主题间关系，并用 wikilink 引用来源；标题唯一时链接用标题，同名页用明确路径消歧。
3. 新建综合页仍需查重，更新已有页走补丁流程。旧文档的重构标记、归档或取代关系按授权处理，避免静默覆盖历史结论。

### 7. 归档

1. 确认要归档的文档范围与目标；仅提出候选不等于授权归档。
2. 在授权范围内标为 `已归档`，更新修改时间，移入 `4-历史归档/`，保留来源与历史决策。
3. 检查移动后的链接，追加“归档”日志；之后查询时仅在历史问题需要时引用归档内容。

### 8. Markdown、Bases 与 CLI 专项操作

- **笔记格式**：按 Markdown 参考处理属性、链接、提示框和嵌入，检查实际渲染。正式知识正文的修改仍走补丁流程。
- **Bases**：用户明确要求编辑时，读取现有 `.base` 和相关属性，再修改筛选、公式、展示字段与视图。依据 Bases 参考检查 YAML、字段和公式，并在 Obsidian 中验证渲染；沿用用户指定位置，不能把视图规则当作笔记正文传入 create_note/merge_note。
- **CLI 与插件调试**：命令操作遵循 CLI 参考；插件和主题任务按其中的重载、错误检查、截图或 DOM 验证流程执行。调试示例不构成修改知识正文或其他 vault 的授权。

## 异常处理与交付

- 命令报错、乱码、丢内容、属性缺失或静默无效果时，先检查本机帮助与 gotchas，再有针对性地重试；不能只凭退出码认定成功。
- 移动后检查未解析链接；写入后检查正文及属性，只有验证成功才报告已完成。
- 交付时说明实际读取或修改的文档、审查状态、存放位置、验证结果及未决项。
- 本 Skill 的环境准备从用户已安装 Obsidian 开始。云同步、Git 提交与推送按用户指定范围处理。
