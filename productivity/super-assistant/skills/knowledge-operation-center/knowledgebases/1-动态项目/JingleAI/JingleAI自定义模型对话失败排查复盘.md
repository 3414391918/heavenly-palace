														# JingleAI自定义模型对话失败排查复盘 1

> [!info] 实测已恢复 · 知识草案待审查
> 2026-09-18，本地预发开发版在将自定义模型显示名称改为接口模型名、完整重启后，对话实测返回 `OK`。用户确认当前已能使用；自定义模型配置体验优化优先级低，暂不处理。本次恢复未修改业务源码，不能视为产品缺陷已经修复。

## 适用范围与结论

本案例针对 JingleAI 桌面端 `apps/desk`，分支 `feature/202609`，排查时源码提交为 `b48f7cc068b7f7debe5d591e303db89888911d4a`。开发版 manifest 为 `2026.9.17-beta.1`，从 joy-desk 根目录执行 `pnpm dev:desk`，使用内场预发配置。启动入口使用本机 Node `v24.18.0`、pnpm `10.33.0`。

本次出现两个连续问题：

1. **模型身份字段错位。** 请求携带的 `id` 被赋为接口模型名，而取密钥时的目录查找只匹配本地 `id` 或显示名称 `name`，最初没有命中已保存的自定义模型。
2. **改名没有立即进入聊天内核。** 显示名称虽已写入配置文件，内核模型快照仍是旧名称，进程内还有模型缓存。完整重启后，新名称进入内核目录，按名称匹配得以命中，真实对话成功。

可复用的判断是：**连通性测试成功，不代表真实对话走了相同的配置、凭据与执行路径；配置落盘，也不代表所有进程已刷新。**

## 现象与对照实验

| 观察或实验 | 实际结果 | 能说明什么 |
|---|---|---|
| 设置中的自定义模型连通性测试 | 用户测试通过 | 该测试路径使用的地址、模型名和密钥可用；不能据此证明聊天路径取到了密钥 |
| 本机安装的生产客户端 | 用户反馈同一自定义模型可用 | 需要比较客户端版本与实现，不能只比较预发/生产域名 |
| 开发版自定义模型聊天 | `No API key for provider: openai-custom-1789641313381-kepo` | 优先追踪本地凭据解析与模型身份，不先假设模型服务不可达 |
| 开发版另建 Claude 会话 | 实测成功 | 开发版整体聊天链路可工作，故障集中在自定义模型路径 |
| 把显示名称改为接口模型名后直接重试 | 仍报同样错误 | 需要核对配置传播与缓存，不能仅凭设置页新名称判断运行时已更新 |
| 保留改名，完整重启后新建自定义模型会话 | 返回 `OK`，日志 `outcome=success` | 本次组合操作可恢复使用 |

本次还观察到：在失败会话里切换模型后点击旧消息的“重试”，仍可能复用原请求的模型。因此，比较不同模型时使用明确选好模型的新会话，并以日志中的实际请求字段为准。

## 代码证据：密钥存在，为什么仍取不到

以下路径相对于 joy-desk 仓库，行号对应排查时源码；升级后应按函数名重新定位。

1. `apps/desk/backend/kernels/jingle/jingle-gateway-kernel.ts:340` 的 `toGatewayModelPayload` 将请求 `id` 设为 `cfg.apiModelId || cfg.modelId || cfg.id || requestedModelId`，另外用 `registryId` 保存本地 ID。本例请求的 `id` 因而成为接口模型名。
2. `packages/jingle-ai-claw/src/core/engine/chat-stream.ts:453` 构造 `fullConfig` 时使用 `id: mc.id`；这条路径没有把 `registryId` 保留为后续取密钥的查找身份。约第 513 行调用 `sanitizeRuntimeModelConfig`，传入对话宿主的配置不含原始密钥。
3. `packages/jingle-ai-claw/src/agents/JoydeskChatHost.ts:1142` 的 `hydratePiRequestModelAuth` 调用 `getModelByIdOrName(cfg?.id || request.modelId || '')`，随后从命中的 `live.apiKey` 回填密钥。它还尝试已注册适配器的密钥；本例同时存在 Provider 注册 ID 带地址后缀的差异。
4. `packages/jingle-ai-claw/src/core/config/models.config.ts:3923` 的 `pickModelByIdOrName` 依次匹配精确 ID、精确名称、忽略大小写的 ID、忽略大小写的名称，**不匹配 `apiModelId`**。第 3978 行的 `getModelByIdOrName` 使用此函数查询当前模型目录。

因此最初的目录查找关系是：

```text
查找键：deepseek-tavern-v2-pro-xhigh
本地 id：custom-1789641313381-kepo      → 不相等
本地 name：酒馆专用大模型             → 不相等
结果：没有找到该条配置，无法从它取回 apiKey
```

连通性测试走另一条路径：`models.config.ts:3662` 的 `testCustomModel` 按保存的自定义模型 ID 取得配置，直接使用该条配置的 `apiKey` 和接口 `modelId`。这解释了“测试通过、聊天失败”能够同时发生。

安装版与开发版也并非同一套运行实现：当时核对的安装包版本为 `2026.9.10`，使用旧对话/适配器路径，`OpenAIAdapter` 直接读取 `this.config.apiKey`；开发分支使用 `JoydeskChatHost` 与 Pi 的凭据回填路径。因此不能将差异概括为“开发环境天然需要再次查询、生产环境天然不需要”。这是本次版本对照结果，不能推广到后续安装包。

## 可复用的排查顺序

1. **固定环境和启动批次。** 记录分支、源码提交、安装包版本、账号、启动命令和日志文件；先防止混用生产安装版与开发版的证据。
2. **从精确错误定位阶段。** 对 `No API key for provider` 先检查凭据解析。连通性测试已通过时，避免反复更换网络或 API key 而没有新证据。
3. **把配置和请求字段并排比较。** 分清本地 ID、显示名称、接口模型名、Provider ID；沿“前端选择 → Gateway 载荷 → 内核请求配置 → 取密钥函数”检查何处发生转换或丢失。
4. **先搜特征，再沿 traceId 追踪。** 在当前本地启动日志中找到报错和对应请求，取得 traceId 后用它关联执行终态；不能仅凭屏幕当前选中的模型推断旧消息重试使用的模型。
5. **对比成功与失败路径。** 模型连通性测试、真实聊天、不同客户端版本应分别看实现；用一个成功模型的新会话缩小故障范围。
6. **配置变更后核验三层状态。** 同时检查用户配置文件、内核快照、缓存/进程生命周期。保存成功是第一层结果；不要跳过后两层直接宣布修复无效。
7. **用真实对话完成闭环。** 明确模型，新建最小会话，要求只返回固定短文本、不调用工具；同时确认 UI 回复和同一 traceId 的成功终态。

本次用户要求截图必须来自直接打开的原始文件或实际应用画面。证据展示应遵循这一要求，不能把重新排版的摘录页截图称为原始文件截图。知识正文记录字段、路径和来源，不保存 API key 明文。

## 用户决策：体验优化暂缓

**2026-09-18 用户明确决定：问题已解决，目前自己能用即可；自定义模型配置功能优先级低，暂不处理体验优化。** 本文只保存改进方向，不代表已立项、已排期或授权本轮修改代码。

若未来重新排期，可考虑：

- 让本地配置 ID 在跨进程传递中保持稳定；接口模型名只用于模型调用，显示名称只用于展示，取密钥不依赖用户手工对齐名称。
- 自定义模型保存后同步刷新内核目录及相关进程缓存，验证编辑后无需重启即可生效。
- 统一 Provider 注册与密钥读取时的身份，避免带地址后缀与不带后缀的标识不一致。
- 增加真实聊天路径的验证或更明确的诊断提示，区分“没有配置密钥”“配置未匹配”“配置尚未刷新”。

重新评估的条件是：自定义模型成为团队常用能力、更多用户受到影响，或现有绕过办法不再稳定。届时仍由用户重新确定优先级，不把这些条件视为自动启动开发的指令。
