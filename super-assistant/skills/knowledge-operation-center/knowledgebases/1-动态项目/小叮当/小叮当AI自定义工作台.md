这是一套在小叮当当中落地的一套通用解决方案，具体的流程就是其它应用或者业务系统通过在小叮当上面通过上架申请，将应用投放给指定用户进行使用，创建人可以在小叮当上对应用进行编辑。目前千机阁上的应用已经打通这套流程，后续的话像数据看板，joydata，热点营销或者其它业务系统也都会通过这套流程接入到小叮当上面来。
以千机阁应用为例，这套流程的大致实现思路是用户在小叮当的工作台下面选择某一个应用进行上架申请，上架申请过程中会输入指定的可见用户和千机阁应用的版本号，版本号是从千机阁上拉取的，申请成功后。所有的系统管理员会在京me上收到这条申请消息，通过消息卡片进入cloud管理后台，审批通过后指定的可见用户即可在小叮当的工作台当中预览和使用这个应用，但是不提供编辑入口。
**在开发的过程中遇到的问题是，已经申请成功并且上架的应用，或者正在申请的应用，如果千机阁那边对该应用进行了版本回滚，要怎么处理呢？**
在千机阁那边会对每个应用的每个版本保存一份codeid作为版本的唯一标识，用户在小叮当申请上架应用的时候会把应用名称，还有应用版本的codeid一起提交到小叮当的cloud端，cloud端再向千机阁应用发起登记，说白了就是在千机阁那边记录一下“小叮当可以使用应用P的A版本”这个委托关系
申请通过后，可见用户在小叮当上想要预览和使用应用需要经过两层校验，cloud端负责验证该用户是不是这个应用的可见用户，千机阁那边负责验证之前登记的委托还有应用的codeid都存在，并且会给cloud后台返回一个预览码，后续可见用户在小叮当使用应用时就通过这个预览码打开会话。预览码是通过签名申请的。
管理员在cloud后台打开申请详情或者提交审批的时候，cloud会向千机阁确认一下当前版本的codeid还存不存在，千机阁在版本回退或者应用删除的时候都会把codeid删除，如果不存在的话就会撤销对应的委托，并标记申请失效。
如果审批通过后，可见用户在刷新或者打开应用的时候，cloud也会向千机阁确认一下当前版本的codeid还存不存在，不存在的话撤销委托，标记上架失效并清空生效记录。
**那直接拿codeid解决版本回退问题不就行了，还记录这层委托关系干什么？**
如果一个用户正在使用V3版本的应用，但此时V4版本已经申请并成功上架了，如果没有委托记录的话，正在使用V3版本的用户还能正常发请求，委托记录可以阻止这种情况的发生。V4 审批通过后会撤销 V3 委托。**撤销成功后**，千机阁会拒绝旧会话后续向千机阁发出的业务请求。
千机阁是在**业务接口执行前**拦截旧请求的：
1. V4 审批通过后，Cloud 通知千机阁撤销 V3 委托。千机阁把它标为“已撤销”。
2. 已打开的 V3 页面查询或提交数据时，会在请求中带上此前取得的预览码。
3. 千机阁根据会话找到它关联的 **V3 委托**。发现委托已撤销，就返回“页面委托已撤销”，不再执行这次业务数据请求。

# 执行路径

1. **明确需求和界面位置。** 用户要求从最新 `feature/202609` 开发：自己加入“我的工作台”的页面可以申请上架，设置页面名称、独立于千机阁分享协作人的可见用户和固定版本；Cloud 管理员审批，通过或驳回后允许重新申请。先在本地启动内场桌面端，按用户截图把“上架设置”放在工作台应用右侧“⋯”菜单，再做出弹窗供用户确认位置和样式。

2. **确定三个代码范围与任务分支。** 用 Git 状态、分支、diff、仓库规则及 `rg` 定位 JoyDesk 的 `apps/desk`、`apps/cloud` 和千机阁的服务端 `qianjige-service`、前端 `ai-create-html`。JoyDesk 首期分支为 `codex/feature-20261014-workbench-publication`；千机阁服务端为 `codex/feature-20261014-page-publication-rollback`，前端后续为 `codex/feature-20261014-page-publication-viewer`。用户后来指定 JoyDesk 集成到 `feature/20261015-xdd-channel-preview`，千机阁以最新 `pre` 为渠道方案依据。开发时保留其他任务的工作区改动。

3. **设计独立上架数据和预发脚本。** Cloud 建立 `page_publication`（页面当前/生效指针）、`page_publication_request`（每次申请与审批记录）、`page_publication_audience`（可见用户）、`page_publication_snapshot`（早期内容留档）四张表，并增加“页面上架管理”菜单和管理员 API 权限。编写 Flyway 迁移及手工预发脚本 `apply_page_publication_20261014.sql`，由用户在预发库执行；后续收件人字段和 `code_id` 分别用增量脚本补齐，没有把预发手工建表误写成自动迁移已运行。

4. **完成桌面申请入口和状态弹窗。** `SidebarAppItemMenu.vue` 加“上架设置”，弹窗和组合逻辑读取本人当前申请、历史与千机阁版本列表。普通 H5 不显示版本；千机阁只能选一个固定版本。审批中禁止重复提交；通过或驳回后可改配置重提，驳回原因和状态在重开弹窗时回显。提交带 `expectedRequestId`，避免旧弹窗覆盖后来发生的申请。

5. **完成 Cloud 审批页和服务端约束。** Cloud Web 的 `/menu/page-publications` 展示申请人、页面、可见范围、申请时间、审批状态和历史，系统/租户管理员可审批并填写驳回原因。后端核对当前用户确为工作台页面所有者、租户边界和管理员角色；同页申请用行锁与状态条件更新，重复审批或竞态返回冲突；只在审批通过时替换生效申请，保留旧审批记录供追溯。

6. **首版固定内容与回退方案。** 初版因版本号可重复而在 Cloud 保存千机阁代码、依赖与回退代次的不可变快照，并让千机阁新增回退状态接口。Cloud 在申请、审批和受众读取时核对所有者与代次；发生版本回退后使旧申请失效、清空生效指针，修改页面后必须重新申请。评审补出两个坑：版本号本身不能证明内容未变；MySQL RR 事务可能拿到旧审批快照，因此审批更新必须再次检查失效状态。

7. **复用“指定版本分享”的代理。** 直接从桌面读取千机阁版本曾出现版本列表错误；按用户指引复用分享弹窗的 `getPageInfo` 和桌面后端 `/api/qianjige-proxy/page-info`，从 `codeList` 构造 V1/V2 等选项。Cloud 仍用申请人的当前票据向千机阁独立校验所有者和版本，不信任桌面下拉框或前端自报的代码内容。

8. **搭起本地 Cloud 预发联调环境。** 本机连 Cloud SSO 的 JSF 注册中心 `6.112.*:40660` 超时，查知识库《资讯配置投放功能》的本地开发记录后，Cloud 改用既有 dev mock 登录配置、连接预发 MySQL，关闭本地不适用的 Flyway、业务定时任务和 Temporal，并只监听回环地址。桌面端指向本地 Cloud，Cloud Web 用 `http://local.jd.com:8081` 打开；这种联调验证了业务链路，但不等于真实预发 SSO 验证。

9. **先完成 H5 申请与审批闭环。** 用户执行首批 SQL 后，用本地桌面和 Cloud 管理页实际走通：H5 测试页提交、审批中不可改、驳回并回显原因、修改后重提、审批通过和历史保留。针对 Cloud 跑 JUnit/MySQL 测试、桌面跑 Vitest/类型检查、Cloud Web 构建；测试记录保留在 Harness。此时千机阁预发尚未部署回退接口，本地 MongoDB 连接也超时，所以不能把 H5 闭环称作千机阁回退端到端通过。

10. **部署千机阁协议并验证真实回退。** 千机阁服务端回退改动提交为 `428fb29`，经 MR #2 合入 `pre` 后由用户确认已部署。随后在隔离测试页生成 V1、V2，上架并审批通过 V2；取得用户确认后把该测试页回退到 V1。Cloud 下一次详情核验将旧 V2 标记失效、清空生效指针；重新申请并审批 V1 后才重新上架。只验证了这个实际回退场景，没有把“同版本号重新生成”说成已经端到端测试。

11. **排查两套登录态误判。** 联调出现“千机阁版本校验失败”和后台审批对千机阁有效 Cookie 的错误预判：Cloud SSO 与千机阁认证并非同一套票据，Cloud 的预校验会错误清掉可用的创建者凭证。改为创建者主动操作时使用当前票据，服务端缓存经千机阁确认的票据，审批时交千机阁做真实鉴权；不再用 Cloud SSO 预判替千机阁判定登录。缓存记录最长保留 30 天，**不等于 Cookie 一定有效 30 天**；失效时上游请求仍会拒绝，需要作者重新打开设置刷新票据。曾讨论独立服务密钥方案，用户决定维持 Cookie 方案。

12. **补全可见用户的工作台体验。** 用户明确上架的核心是指定人员能使用页面，但不能通过工作台修改页面源码、版本和配置，页面内业务数据操作仍允许。Cloud 增加 `/api/page-publications/received`，只返回当前租户、当前用户命中的生效申请；Desk 与本人应用放在同一工作台列表，以不同图标/认证标识区分，收件条目只有打开入口，没有编辑、分享、上架或移除菜单。申请人把自己选作可见用户时也不重复显示另一份收件条目。

13. **探索首版收件人预览与权限边界。** 早期千机阁服务端/前端分别增加固定快照的展示代理、业务数据访问和 HTML 预览；用户要求后也短暂放开 Vue3 页面。独立评审发现同源 Vue3 脚本、预览代理白名单、WebSocket 和动态库表绑定都可能扩大收件人能力，于是收窄代理与数据权限。这里“不能编辑”指服务端不给源码、版本和配置的修改权限，不代表浏览器里运行的 HTML/JS 对收件人保密；自定义 H5 的源码由外站维护，Cloud 只控制工作台入口。

14. **处理收件人增量表和本地域名坑。** 用户执行 `apply_page_publication_received_20261014.sql` 后，只读核对新增列与 API 菜单绑定。桌面经本地 `http://local.jd.com` 代理时一度返回 401：后端转发漏掉浏览器会补的登录短票，且本地 HTTP 与预发 HTTPS 的 Secure Cookie 行为不同；复用现有票据筛选规则后，自己的工作台列表和 Cloud 收件接口恢复。页面收件列表刷新依赖加载、应用变化和窗口重新获得焦点，已打开的浏览器代码不能被远程擦除。

15. **分批提交并保留可回退点。** 初版申请审批为 JoyDesk `bfd606683b`；收件人为 `eaa01bbfb8`、同列展示为 `1ccdf2efb3`；Vue3 首版兼容为 `7bec17b04c`。按用户授权提交、推送 JoyDesk 与千机阁服务/前端开发分支并创建面向预发的 MR；千机阁前端预览提交包括 `a758074`、`8b99f0e` 及预发构建 `8744688`。这些 Git 阶段分别是开发、提交、合入或部署，不能把 MR 已创建等同于服务已发布。

16. **给审批链路加京ME通知。** 在原申请/审批事务后复用小叮当现有 `JmeMessageService`：提交申请通知后台管理员，卡片带申请人、页面和 Cloud 审批管理页链接；管理员从链接查看待上架页面、可见范围、菜单名称和申请时间。通过/驳回时记录审批人及时间，并给申请人发送结果卡片。消息发送失败只记日志，不回滚已经入库的申请或审批结果；提交为 `202ecd8ee6`。

17. **按正常流程验证消息而非直接发测试消息。** 本地用小叮当提交申请，经京ME卡片链接进 Cloud 审批，再验证通过/驳回通知和桌面状态回读，并给 `wangshaofan.7` 做收件验证。排查“部分管理员未收到”时，发现管理员列表混入不应接收京ME的 `AI_AUDITOR` 系统账号，已过滤；其余 11 位人工管理员的京ME代理仍返回失败码/空结果，Cloud 无法判定其京ME投递资格，需京ME侧排查，不能写成全部管理员均已送达。服务端补日志记录上游 code/message；登录 helper 故障改报不可用，提交为 `21a67b4a7f`。

18. **重新核对千机阁最新 `pre` 的版本语义。** 用户要求重设回退方案后，拉取千机阁 `pre` 并查看 `codeList`、页面回退/删除逻辑和渠道接口。确认每次生成的版本以独立 `codeId` 标识；回退截掉后续版本时其 `codeId` 消失，同号版本重新生成也得到新 ID。不能只用 V3 这样的版本号作审批准据；早期 `publicationRollbackToken/queryPublicationState` 方案不再是当前渠道预览主链路。

19. **接入千机阁的渠道委托与签名授权。** 千机阁 `pre` 增加页面所有者用自己的登录态登记 `pageKey + codeId` 的固定版本委托、平台管理员配置渠道和公钥，以及上游服务端签名领取授权的接口。Cloud 保存申请的 `codeId` 并在提交时登记委托；可见用户范围仍由 Cloud 数据库独立判断，千机阁只验证该渠道有委托、版本仍在和运行时库表权限。Cloud 侧 `apply_page_publication_code_id_20261015.sql` 是这次演进的增量脚本。千机阁渠道实现对应服务端 `ea92165`、前端 `ede34ab`。

20. **把收件人打开动作切到渠道预览。** JoyDesk `feature/20261015-xdd-channel-preview` 合入前述上架代码后，以 `894315229d` 将千机阁收件页面改为 `/#/channel-preview`：Cloud 核对审批已通过且当前用户在可见范围内，再按固定 `codeId` 向千机阁签名领取授权和一次性预览码；桌面后端取回预览 URL，前端仅允许千机阁白名单域名并把码交给预览壳。预览壳用短时一次性码换会话，按该会话拉固定版本并代发业务请求；私钥、长期授权 ID 不交给页面脚本。自己的页面继续走原预览入口。

21. **区分 `codeId`、委托、预览码各自作用。** `codeId` 证明“是哪份代码”，不证明“这个用户可见”；Cloud 受众检查解决后者。委托证明页面作者允许小叮当渠道使用这一版，并可在撤销时使已领取的授权和会话失效。预览码只负责把已获授权的服务器决定安全交给浏览器，短时、一次性，不能拿 `codeId` 直接充当用户访问凭证。用户多轮追问后，用固定版本委托、申请临时码和 V3/V4 切换的简明时序图解释这一层关系。

22. **梳理审批前、审批后回退与旧会话。** 待审时回退若截掉申请的 `codeId`，管理员打开详情或审批前的 Cloud 核验使申请失效，不能继续批准。通过后回退，收件人刷新列表或打开页面时 Cloud 再核验，清空旧生效指针并撤销委托；新版本要重新申请审批。若 V4 审批通过替换 V3，Cloud 撤销旧 V3 委托，千机阁在旧预览会话后续业务请求进入处理前检查委托并拒绝；已经在浏览器里显示的画面不会瞬间消失，刷新列表后旧条目才消失。千机阁普通删除/软删除与 `codeId` 物理消失并非一回事，访问是否允许还要看源页状态与委托。

23. **记录验证证据与尚未覆盖的边界。** 首期本地 H5 申请/驳回/通过闭环、千机阁预发 V2→V1 回退、Cloud 管理页、桌面状态、定向单元/MySQL 测试和京ME申请/审批链路均有相应记录；渠道方案又补 Cloud JUnit、Desk Vitest、后端代理和千机阁 Node/前端构建测试。部分检查受本机 JSF/Mongo 网络、真实 SSO、双账号预发环境及京ME代理投递失败限制，不能因为本地 dev mock 或构建通过就推断完整预发投递与所有页面类型均已验证；千机阁渠道预览壳的 Vue3 兼容也应以实际预发页面验证为准。

24. **沉淀图文与工具链。** 把提交申请、管理员审批、固定版本委托、临时预览码、回退两种时机等原图及 Mermaid 源文件放在本目录 `assets/` 并在“图例说明”引用；按用户要求整理到 JoySpace 云文档，并用 Obsidian CLI 清理未被正文引用的图片。实际排查/开发用到 Git 提交与 diff、`rg`/仓库文档、浏览器和桌面 UI、Cloud/千机阁 HTTP 接口、MySQL 脚本与查询、Maven/JUnit、Node 测试、Vitest、前端构建、京ME联调和 Obsidian CLI。这里的测试结论来自对应阶段记录，整理执行路径时没有重新跑全量端到端测试。
