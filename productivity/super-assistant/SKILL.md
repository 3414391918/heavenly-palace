# Super Assistant

本 Skill 是研发问题处理的能力入口。当前不规定固定的调用顺序；根据问题现象选择一个或多个原子 Skill，并按照各原子 Skill 自己的 `SKILL.md` 独立执行。

## 原子 Skill 能力

- `code-operation-center`：阅读 Java 代码，分析单应用或跨应用调用链、状态机、持久层以及 RPC、HTTP、MQ 边界。
- `log-operation-center`：查询生产、预发和测试环境日志，追踪请求链路、启动异常和运行时配置。
- `data-operation-center`：查询数据库或缓存，核对业务状态和数据事实。
- `equity-operation-center`：查询或操作权益营销后台，核对活动、奖品、渠道和规则等平台配置。
- `jmq-operation-center`：处理 JMQ 问题，核对 Topic、生产者、消费者、订阅关系和消息投递。
- `mock-operation-center`：为联调或测试配置接口 Mock。
- `test-operation-center`：设计并执行需求测试、联调验证和回归检查。
- `deploy-operation-center`：处理分支、提交、公共包发布、构建、部署、配置、JSF 和部署后验证。

## 解决问题时怎么使用

1. 先明确问题涉及的应用、环境、时间、关键 ID、期望结果以及允许执行的操作。
2. 根据当前线索选择最相关的原子 Skill。选中后完整阅读它的 `SKILL.md`，并遵守其中的操作要求。
3. 有报错或现场请求时通常先查日志；需要解释系统行为时使用代码分析能力；需要实现需求或修改代码时使用代码编写能力；状态或数据不一致时结合日志、代码和数据查询。
4. 涉及活动、奖品、渠道等平台配置时使用权益平台能力；涉及消息生产、投递或消费时使用 JMQ 能力。
5. 需要复现和验证时使用 Mock、测试能力；需要提交、发布或部署时使用部署能力。
6. 需要形成或更新技术方案、接口说明、复盘等工作文档时，使用文档能力组织已有证据；需要补充事实时再配合相应原子 Skill。
7. 不要求固定顺序。每获得一条新证据，就重新判断下一步最合适的原子 Skill，直到事实能够解释现象并完成必要验证。
8. 解决问题后的结论一定要带有截图依据

## 独立判断与业务规则核验

- 用户的质疑或修改建议是需要核验的线索，不自动等于正确结论。有相反证据时应明确说明不同意见及依据；没有新证据或需求变化，不因用户态度改变而反复推翻判断。用户补充业务规则或调整目标时，应据此重新评估。
- 区分“找到了原因”和“证明代码有缺陷”。命中开关、黑白名单或降级策略而跳过处理，可能正是预期行为；应结合需求、原有实现、配置说明和目标环境的生效值判断，不能为了让结果出现就绕过规则。
- 判断是否重复校验，要看校验的业务含义和职责。业务层判断“优惠是否被屏蔽”，发送层判断“该渠道是否允许上报 MT”，二者并不重复；不能仅因发送前又有一次判断，就认定应当删除。
- 复用或删除既有规则前，核对它的适用范围。新功能是否受原有名单约束，应由业务规则决定，不能默认新旧逻辑必须共用或必须隔离。修改代码判断或配置值前，说明会改变哪些上报、渠道和已有行为；规则与目标存在实质冲突且尚未明确时，先说明冲突并澄清，而不是无条件执行建议。

本次案例：`datamillUse` 命中 `mtSendBlackDeliveryChannels`（MT 报送黑名单渠道集合），零售业态管控虽已记录失败，仍按渠道策略停止上报。确认该名单约束所有该渠道的 MT 记录后，发送类保留判断是正确的；不能为了查到这条客诉明细，擅自删除判断或移除名单项。若后续业务明确要求例外，再按新的适用范围实施。

## 使用边界

- 原子 Skill 彼此独立，本 Skill 不调用或复制它们内部的脚本、模板和状态文件。
- 结论应区分已确认事实、合理推断和未决项。配置类问题应在实际归属平台和目标环境中核验。
- 涉及数据库写入、平台配置、发布、部署以及预发或生产变更时，必须遵守用户授权。
- 不在记录或输出中泄露密码、Token、Cookie、密钥、完整用户标识和未脱敏生产报文。
