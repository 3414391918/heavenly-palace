# 公共包升版、发布与消费方更新

## 1. 判断是否属于公共包

以下模块通常按公共包处理：

- 对外或跨应用使用的 API、JSF 接口、DTO、枚举模块。
- common、persistence 等被多个应用依赖的基础模块。
- 需求文档明确要求先 `deploy` 再更新开发应用的模块。

先从消费方 POM 和依赖树确认真实使用关系，不凭模块名称推断。

## 2. 版本命名

项目专属规范优先。通用规则是：先读取最新 `origin/master` 中该模块 POM 的版本，把 master 的补丁版本加一，再在 `SNAPSHOT` 前插入需求简称。升版基线只能来自 master，不能来自开发分支当前版本。

```text
master: 1.0.67-SNAPSHOT
需求版: 1.0.68-baitiao-SNAPSHOT
```

计算版本前至少核对以下三项：

1. 使用 `git show origin/master:pom.xml`（多模块项目使用对应模块 POM 路径）读取 master 版本，不能只看当前工作树的 POM。
2. 区分“master 基线版本”和“需求分支自定义版本”。例如 master 为 `1.0.68-SNAPSHOT`、需求分支已经是 `1.0.69-baitiao-SNAPSHOT` 时，新增一次需求内修改仍保持 `1.0.69-baitiao-SNAPSHOT`，不能误升为 `1.0.70-baitiao-SNAPSHOT`。
3. 只有 master 基线推进、项目规范明确要求再次升版，或当前候选版本被其他需求占用时，才重新计算需求版本；重新计算仍以最新 master 为起点。

禁止继续使用已被其他开发者或其他需求占用的自定义版本。若远端仓库已有同名快照，先确认它是否属于本需求以及覆盖策略。

## 3. 正确顺序

1. 在公共包开发分支合入最新 `origin/master`。
2. 使用 `git show origin/master:<pom路径>` 读取合并后的 master 版本；根据该版本计算需求快照。若当前需求版本已经等于“master 下一版本 + 需求后缀”，保持原版本，不重复加一。
3. 修改公共包自身版本和必要的内部模块引用。
4. 使用项目兼容的 JDK 执行测试。
5. 执行 `mvn clean deploy`，确认制品真正上传成功。
6. 再把新版本更新到全部需求消费方。
7. 测试消费方，然后把最新 `origin/master` 合入消费方开发分支。

不能先更新消费方，再假设公共包稍后会发布成功。

### 同版本 SNAPSHOT 的重新发布门禁

SNAPSHOT 坐标不变不代表制品内容已更新。公共包源码在上一次成功发布后只要又发生变化，就必须重新执行 `mvn clean deploy -U`，生成并上传新的时间戳制品。以下结果都不能代替本轮发布：

- 版本号和上次相同。
- 本地 `test`、`package` 或 `install` 成功。
- 本地仓库或私服中已经存在同名 SNAPSHOT。
- 消费方以前曾经成功构建。

把“最后一次公共包源码变更”与“最后一次成功 deploy”按时间和内容对应起来。无法证明 deploy 覆盖了当前源码时，一律视为尚未发布，不得继续消费方部署或联调。

发布后必须让消费方主动刷新 SNAPSHOT，例如使用 `-U` 重新构建或查看限定坐标的 `dependency:tree`。至少保留以下证据：

1. 公共包仓库、分支、当前提交或工作树变更摘要。
2. 实际执行的完整 deploy 命令及 `BUILD SUCCESS`。
3. 私服上传产生的新时间戳版本或上传记录。
4. 消费方重新解析该坐标的下载记录或依赖树结果。

如果消费方仍命中旧时间戳制品，不能通过修改业务代码兼容旧枚举、旧字段或旧接口来绕过；先清理或刷新依赖解析并重新构建消费方。

## 4. Maven 执行与证据

先读取项目的 `maven-compiler-plugin`、父 POM、README 或部署文档，选择兼容 JDK。不要为了让本机编译通过而修改项目的 source/target 版本。

常用命令：

```bash
mvn clean test -U
mvn clean deploy -U
```

如果项目有 profile、settings 或仓库参数，使用项目文档中的完整命令。

成功标准不只是最后一行出现 `BUILD SUCCESS`，还要确认：

- 所有模块均成功。
- 单测实际执行数、失败数和跳过数符合预期。
- 日志中存在目标版本的上传记录。
- 私服中能够解析新版本，或消费方构建能够成功下载该版本。

若 Surefire 配置允许忽略失败，必须单独检查测试报告；不能把忽略后的 `BUILD SUCCESS` 当成单测通过。

## 5. POM 冲突处理

POM 冲突时分别判断：

- master 引入的新依赖、新插件或父版本需要保留。
- 本需求的自定义版本需要按最新 master 基线重新计算。
- 消费方只更新本需求确实依赖的公共包版本。

不得通过回退 master 的版本号、删除新依赖或批量改写所有依赖来快速消除冲突。

## 6. 失败处理

发布失败时先定位阶段：编译、单测、签名/认证、私服上传、版本冲突或网络。只修复本需求范围内的直接原因。

若失败来自账号权限、私服不可用或共享版本占用，保留完整命令和错误证据，停止更新消费方并向用户说明。
