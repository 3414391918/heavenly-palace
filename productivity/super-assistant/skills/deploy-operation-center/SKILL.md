# 部署操作中心

把代码开发完成后的工作作为一条有检查点的流水线执行。每一步都以实际仓库、制品和环境证据为准，不扩大需求范围，不顺手优化其他链路。

## 先识别本次任务

将用户请求映射到以下一个或多个阶段，只执行已授权的阶段：

1. 前端本地环境、依赖安装、开发服务器启动与页面可用性排查。
2. 单元测试与质量门禁。
3. 创建需求分支、提交和推送。
4. 发布 common、API、persistence 等公共包并更新消费方。
5. 把最新 `origin/master` 合入开发分支。
6. 合入预发或团队共享分支。
7. 构建并部署后端，检查实例和 JSF。
8. 构建并部署前端，验证远端静态资源。
9. 排查部署、启动、配置或调用异常。

先查找并完整阅读当前需求目录中的项目专属文档，例如 `代码推送合并指南.md`、`部署环境.md`、测试报告，以及仓库内的 `pom.xml`、构建脚本和部署配置。项目专属文档优先于本 Skill 中的通用示例。

按任务读取对应参考文件：

- Git 分支、提交、推送、合并和完整性校验：`templates/git-workflow.md`
- 公共包升版、发布和消费方更新：`templates/public-package-release.md`
- 单元测试与质量门禁：`templates/test-and-quality-gates.md`
- 行云后端部署、配置和 JSF 验证：`templates/jagile-backend-deployment.md`
- 前端 Node/包管理器选择、依赖安装、开发服务器启动和常见故障：`templates/frontend-startup-troubleshooting.md`
- 前端测试/预发/生产构建、新老项目发布入口、审批、滚动部署、Clear 发布和生效验证：`templates/frontend-deployment.md`

## 前端本地启动门禁

处理前端启动失败时，先按锁文件、`packageManager`、`.nvmrc`、`engines`、CI 配置和项目文档还原项目预期环境，再复现最小失败。不得一开始就删除 lock、升级依赖、关闭 lint 或改业务代码。

全局安装工具、改 shell 启动文件、切换全局 registry、删除 lock、重建依赖树、批准依赖安装脚本或监听 `0.0.0.0` 都会改变系统或安全边界，必须说明原因和影响并取得对应授权。优先使用项目已有 Node 版本、锁定的包管理器和本地 CLI；仅启动本机访问时优先绑定 `127.0.0.1`。

启动完成不等于可用。必须确认进程持续存活、HTTP 可访问、目标页面可渲染、浏览器控制台没有阻断错误、关键接口或代理符合预期。若临时绕过 ESLint、使用 CLI 覆盖 host/port、重建原生模块或重新生成 lock，最终报告必须逐项披露。详细诊断与已知故障模式见 `templates/frontend-startup-troubleshooting.md`。

## 公共包源码变更自动触发

只要本轮修改了 API、common、persistence 等公共包的 Java 源码、资源文件或对外契约，就自动把“公共包发布并验证消费方”加入当前任务，不得把它仅归类为代码同步、枚举调整、文档更新、提交推送或消费方部署。公共包的本地 Maven `deploy` 是这类代码修改的必要完成步骤，不等同于部署测试、预发或生产实例；除非用户明确说本轮由其发布或禁止发布，否则不等待用户再次提醒。

把公共包发布作为阻断门禁：当前公共包最后一次源码变更之后，必须存在一次对应的 `mvn clean deploy` 成功证据。只要源码又发生变化，之前同版本的发布记录立即失效，必须重新发布；POM 版本未变化、已经执行过 `install/package/test`、私服存在同名 SNAPSHOT，都不能替代本轮 `deploy`。

公共包发布完成前，不得把消费方构建、部署或联调标记为可执行或已完成。详细验证规则见 `templates/public-package-release.md`。

## 建立范围清单

从实际变更、需求分支和依赖关系建立仓库清单。不要把“工作区中存在的仓库”当成“本需求涉及的仓库”。每个仓库至少记录：

- 仓库绝对路径、当前分支、远程地址。
- 本需求修改文件和变更目的。
- 是否为公共包、后端应用或前端应用。
- 上游依赖与下游消费方。
- 需要执行的测试、发布和部署动作。

任何已有的用户改动、未跟踪文件或来源不明的提交都不得覆盖。无法安全隔离时停止该仓库的写操作并向用户说明。

## Git 操作前门禁

进入任何提交、推送或合并动作前，逐仓库确认：

- 当前位于本需求开发分支，而不是 `master`。
- 工作树干净，或者未提交内容已明确属于本需求且当前步骤就是提交。
- 本地开发分支与远端同名分支同步。
- 已记录本地 `master` 的提交号；流程结束时必须保持不变。
- 不存在 `.codegraph`、IDE 元数据、构建缓存等工具文件待提交。

可先运行只读脚本生成审计结果：

```bash
python3 scripts/git_workspace_gate.py \
  --root <工作区路径> \
  --requirement-key <需求分支关键字> \
  --phase pre
```

脚本报错时先解决范围、分支或同步问题，不得绕过门禁继续。

首次创建且尚未推送远端分支时可加 `--allow-unpublished`；提交前工作树确实包含已逐文件确认的需求变更时可加 `--allow-dirty`。这两个参数只改变对应门禁项，不会自动提交或修改任何文件。

## 执行总流程

按依赖顺序执行：

1. 若任务包含前端本地启动，先在不修改项目契约的前提下恢复可重复的 Node 与依赖环境，验证页面和关键请求；需要改源码、配置或既有依赖版本时，转为明确的代码变更并重新确认范围。
2. 完成需求单测和受影响模块测试，记录真实执行数。
3. 若修改公共包，先在公共包开发分支合入最新 `origin/master`；必须读取合并后 `origin/master` 对应 POM 的版本，以 master 版本为唯一升版基线，再确定自定义快照版本并执行 `mvn clean deploy`。不得根据开发分支当前自定义版本继续累加；若开发分支已经使用“master 下一版本 + 需求后缀”，本轮继续沿用，不得再次升一版。同一需求继续使用原 SNAPSHOT 时，每次新的公共包源码变更仍必须重新执行 `clean deploy`。
4. 公共包发布成功后，更新开发应用依赖版本并完成测试。
5. 逐仓库在开发分支执行 `git merge origin/master`；禁止切到或修改本地 `master`。
6. 仅解决真实冲突，保留 master 的正常演进和已经验证的需求变更，不夹带格式化、清理或额外优化。
7. 重新运行受冲突影响的测试与完整性门禁。
8. 普通推送开发分支，禁止 force push。
9. 部署时锁定应用、环境、分组、IP、构建参数、制品版本、Git 提交和构建人。
10. 验证实例启动、运行时配置、JSF 提供者或消费者关系、前端资源版本和关键业务入口。

合并完成后运行：

```bash
python3 scripts/git_workspace_gate.py \
  --root <工作区路径> \
  --requirement-key <需求分支关键字> \
  --phase post
```

同时人工确认：

- `origin/master` 是当前开发分支祖先。
- 本地与远端开发分支同步，工作树干净。
- 相对 master 没有意外删除源码、测试或配置。
- 本地 `master` 提交号与开始时一致。
- 测试报告中的执行数、失败数和跳过数符合预期。

## 部署边界

- 用户未指定共享测试实例时，先通过项目部署文档和现有配置确定目标；仍有多个有效目标时必须询问用户。
- 测试环境也可能被多人共用。覆盖他人制品、切换实例流量或修改共享配置前必须确认。
- 预发和生产环境必须有用户的明确授权，不从“部署一下”自动推断。
- JSF 是否可用以注册中心的实际提供者状态为准，不能只看进程是否存活。
- 行云变更任务显示“完成”只表示平台动作结束，不代表 JSF 已成功上线；必须继续核对 Provider 数量、alias 和实例状态。
- 遇到实例进程正常但 JSF 数量为 `0` 或 J 标灰色时，优先按“Spring 容器可能已退出、后台线程仍维持 JVM”排查当前启动批次的业务日志和最终运行时配置。
- 遇到未解析的 `${jsf.*}` 占位符时，不要只补当前异常中的第一个 key；以实际部署提交和构建 profile 为准，检查同一 Spring/JSF 配置块引用的全部 alias、timeout 等关联 key 与实例最终配置的差集，再一次性修复目标分组。完整步骤见 `templates/jagile-backend-deployment.md`。
- 遇到 `[JSF-22010] No alive provider` 时，按“接口 + alias”二元组核对消费端最终配置和注册中心；不要因一个错误 alias 覆盖仍被其他调用方使用的主 alias。测试环境确需兼容时，保留主 alias 并增加环境级第二注册，重部署后验证 Provider 数量增量和两个 alias 的实际注册记录。
- 行云分组配置变更后，通常要用同一制品重新部署以注入配置；单纯重启不一定生效。
- 重新部署后先等待日志出现 Provider 导出完成并达到预期数量，再执行 JSF 上线；过早上线会因注册中心尚无 Provider 而失败。
- 用户明确说“这一轮我来部署”时，完成代码和测试后立即停止部署动作并通知用户。

## 完成标准

最终报告只写可验证事实，至少包括：

- 实际处理的仓库、分支和提交号。
- 前端本地启动使用的 Node、包管理器、lock、命令、访问地址，以及任何环境覆盖、依赖树重建或临时绕过。
- 公共包发布版本、消费方依赖版本和 Maven 结果。
- 合并来源、冲突文件与处理依据。
- 单测命令、真实执行数和结果。
- 部署目标八元组：应用、环境、分组、IP、构建参数、制品、提交、构建人。
- JSF、日志或前端资源的部署后验证结果。
- 未执行的阶段及原因。

任一关键验证失败时，不得宣称流程完成。
