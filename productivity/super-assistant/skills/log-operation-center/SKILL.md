# 日志查询操作中心

## 默认工作流

**网页定位实例，tmux 读取日志。** 已有可信的应用、环境和 IP 时直接复用连接，不必每次打开网页。tmux 管理本机终端会话，服务器连接仍通过 SSH/堡垒机；它不会扩大账号权限，也不保证网络中断后远端进程继续运行。

1. 从用户请求、调用方配置或已有项目知识确定实际后端、环境、时间范围与查询关键字；信息已明确就继续，不重复询问。本地启动的前端可能调用远端生产后端，日志应查实际处理请求的服务。
2. 实例不明确时用行云/Digger 网页定位应用、分组、IP；部署或启动问题再核对制品、提交和部署时间。以当前页面和运行事实为准，截图只作参考。
3. 按 [tmux 安装与查询操作](references/tmux-log-query.md) 检查本机工具、复用/创建会话，经项目规定的 SSH/堡垒机路径进入目标。登录后核对 hostname/IP，先确认实际日志文件，再按 traceId 和时间查询。
4. 返回命中的实例、文件、时间、关键异常及查询覆盖范围；没有命中要说明是否检查了轮转文件、其他节点。登录成功不等于读到日志，读到日志不等于复现了问题。

查询默认只读。不要因查日志而重启、发布、修改数据库/配置或清理日志。沿用已有授权和凭据机制；密码、Cookie、令牌不得写入 skill、命令历史或查询报告。认证需要用户参与时保留会话，说明当前提示，请用户在本机终端完成，勿索取聊天中的密码。

## 工具选择与入口

| 场景 | 首选方式 |
|---|---|
| 已知应用、环境和实例 IP | tmux → SSH/堡垒机 → 目标日志 |
| IP、分组或请求落点未知 | 网页定位；必要时 Digger 按 traceId 跨实例搜索，再用 tmux 读取命中实例上下文 |
| 配合复现、观察实时日志 | tmux 内限时跟踪目标文件，查询结束停止跟踪；多实例落点不明时用 Digger 聚合 |
| SSH 无权限、不可达、认证暂无法完成 | 已获授权的网页日志/终端作为备用，不绕过访问控制 |
| 实例已销毁或本机轮转日志已删除 | Digger 历史/归档日志；说明可用保留时间 |
| 启动失败、JSF 或运行时配置问题 | 网页核对制品与实例，tmux 读取启动日志/目标配置；见 [测试运行时排查](templates/jagile-test-runtime-logs.md) |

| 平台 | 入口与用途 |
|---|---|
| 生产/预发 Digger | https://digger.jd.com/appLog/logSearch ，跨实例历史检索 |
| JoyWatch | https://joywatch.jd.com/digger/techApp/overview ，按应用定位；本地日志页以当前导航为准 |
| 生产/预发行云 | 使用目标应用的实例列表链接，核对分组/IP；勿从应用名猜测固定分组 |
| 测试 Digger | http://digger.jdd-office-beta.local/appLog/logLocal |
| 测试行云 | http://jagile.jd.com/jdosCD/lstest/apps ，按当前导航定位 |

网页备用查询仍优先完整 traceId/完全匹配，设置与事件相符的时间窗口，并核对 IP 和日志文件。业务明细通常在 DETAIL 文件，不一定在 console.log；未订阅文件时可查本地日志或归档列表。`state_cards.json` 和 `images/` 仅在操作对应网页时按需查看。

仅验证连接和日志可读性时，核对文件并读取少量脱敏样本即可，不需要先发起业务请求。真正排障时按以下规则选择关键字。

# 关键字选择

## 确定关键字的目的
1. **精准查询**：能够准确找到目标请求的日志
2. **减少返回结果**：避免返回大量无关日志，提高分析效率

## 关键字选择原则
- **关键字越具体越好**：能够唯一标识一笔请求是最理想的
- **针对日志拼接逻辑**：参考代码中日志打印的拼接方式来构建关键字
- **考虑日志量**：如果关键字返回的日志量过大，需要继续补充更具体的条件

## 推荐的关键字类型（按优先级排序）

### 1. trace_id（最高优先级）
- **最佳关键字**：能够查到这笔请求的所有日志
- **优势**：贯穿整个调用链，最全面
- **使用建议**：如果日志量仍然过大，可以结合其他关键字进行筛选
- **强制要求**：如果日志中包含trace_id，**必须**使用trace_id，不得使用其他字段（如srn、requestId等）

**trace_id 识别方法（必须按顺序执行）**：

**步骤1：优先从用户输入的日志中提取trace_id**
- 日志格式特征：`trace_id` 通常出现在日志的固定位置
- 格式示例：`5041906.73435.17731623853805839`（三部分用点号分隔）
- 日志位置：通常在时间戳之后，类名之前
- 示例日志：`26-03-12.12:34:56.789 [pool-2-thread-1] INFO  UserService 4526003.71425.17732884480285895 PFTID-123 - 处理用户请求`
- 提取规则：按应用实际日志字段识别完整 traceId；`数字.数字.数字` 只是一种格式，也可能是 `cloud-...`、`desk-...` 或 `sgm_tid`/`pfinder_tid` 字段值。不得因格式不同丢弃实际链路标识。
- **强制要求**：如果用户提供的日志中包含trace_id，**必须**使用trace_id，不能使用其他字段（如srn）
- **常见错误**：不要因为srn字段在JSON中更显眼就优先使用srn，必须优先使用trace_id

**步骤2：从用户明确提供的trace_id获取**
- 如果用户直接提供了trace_id参数，直接使用
- 如果用户提供了单独的trace_id值，直接使用

**步骤3：从查询到的日志中反向提取**
- 使用其他关键字查询到日志后，从日志中提取trace_id
- 然后用提取到的trace_id重新查询，确保获取完整调用链

**trace_id 样例**：
- 样例值：`4526003.71425.17732884480285895`
- 格式特征：由三个数字部分组成，用点号分隔（部分1.部分2.部分3）

**使用trace_id查询的注意事项**：
- trace_id是唯一的，使用完整的trace_id进行查询最准确
- trace_id在同一请求的所有日志中保持不变，是跨服务追踪的最佳关键字
- 如果用户没有提供trace_id，可以从其他关键字（如用户ID、订单号）查询到的日志中提取trace_id，再进行更精确的查询

**trace_id查询失败时的处理策略（必须执行）**：
当使用trace_id作为关键字查询日志时，如果未查询到结果，**必须**按照以下顺序执行：

1. **第一步：排查查询时间范围是否准确（优先级最高）**
   - 检查默认时间范围是否覆盖了请求发生的时间
   - **关键操作**：如果用户提供的日志包含明确的时间戳（如错误日志），**必须**优先使用该时间戳设置查询范围，而不是使用默认时间范围
   - 如果用户提供了具体的发生时间，调整时间范围到该时间附近
   - 如果用户没有提供时间，尝试扩大时间范围（例如扩大到前后2小时）
   - **必须**使用trace_id重新查询
   - **实践经验**：如果日志文件归档策略导致日志分布在多个文件中，需要确保能够检索到归档日志
   - **最佳实践**：从用户提供的错误日志中提取时间戳，直接设置为查询时间范围（例如：日志时间为"26-03-23.22:58:30"，则设置查询范围为"2026-03-23 22:00-23:59"）

2. **第二步：扩大时间范围再查**
   - 如果调整后的时间范围仍未查到结果，继续扩大时间范围
   - 可以尝试将时间范围扩大到当天（0点到24点）
   - **必须**再次使用trace_id重新查询
   - **实践经验**：有时日志时间戳与请求发生时间有较大差异（如异步处理延迟），建议扩大到前后24小时进行查询
   - **推荐扩大策略**：
     - 默认查询未命中：扩大到前后2小时
     - 2小时仍未命中：扩大到前后12小时
     - 12小时仍未命中：扩大到前后24小时或全当天

3. **第三步：更换次优先级的关键字进行查找**
   - 如果扩大时间范围后仍未查到结果，先核对其他实例、轮转/压缩文件、日志保留期与网页订阅范围，不能据单节点无结果认定请求未发生
   - 按照关键字优先级，选择次优先级的关键字进行查询：
     - 请求标识（requestId、sessionId、srn、交易流水号）
     - 用户信息（userId、用户名、手机号）
     - 业务标识信息（orderId、activityId、productId等）
   - 使用次优先级关键字查询后，**必须**从查询到的日志中提取trace_id
   - 提取到trace_id后，再次使用trace_id进行完整查询

**执行要点**：
- **必须**严格按照第一步→第二步→第三步的顺序执行，不能跳过
- 每一步执行后，**必须**重新评估是否查到了日志
- 只有当trace_id确实无法查到时，才能使用次优先级关键字
- 使用次优先级关键字查到日志后，**必须**提取trace_id进行二次查询，确保获取完整的调用链日志

### 2. 请求标识
- 请求ID（requestNo）
- 会话ID（srn）
- 交易流水号

### 3. 用户信息
- 用户ID（pin）
- 用户名
- 手机号
- 适用于追踪特定用户的所有请求

### 4. 业务标识信息
- 订单号（orderId）
- 活动ID（activityId）
- 商品ID（productId）
- 奖品实例ID（prizeInstanceId）
  - 唯一标识一笔奖品的实例
  - 适用于追踪特定奖品的完整生命周期（发放、使用、取消等）
  - 示例：`"0mn2i7c81I00468wg1130rL8j"`
- 其他业务唯一标识

### 5. 代码日志拼接关键字
- 基于代码中实际的日志打印语句
- 提取日志中拼接的关键参数
- 例如：`logger.info("处理订单:{}，用户:{}", orderId, userId)` 可以用 `处理订单:111111` 作为关键字

### 6. 通过接口识别确定关键字（推荐方法）

当需要查询某个接口的日志但不确定具体关键字时，可以通过接口识别方法来确定查询关键字。

先明确用户问题涉及的接口，再获取接口代码，从代码中找到日志打印的关键字，使用日志打印关键字进行日志查询。推荐使用接口入口处的日志关键字。

## 关键字构建策略

### 单一关键字
- 使用trace_id、orderId等唯一标识
- 适用于需要查看完整调用链的场景

### 组合关键字
- 使用多个关键字组合查询
- 示例：`"takePrize 通用领奖 forceBot"`
- 适用于需要更精确匹配的场景

## 注意事项
- 确保关键字在日志中确实存在
- 避免使用过于通用的关键字（如时间、普通词汇）
- 如果关键字不确定，可以先使用较宽松的关键字，再根据返回结果逐步细化
- 关键字应与应用参数结合使用，以提高查询效率
- **强制要求**：如果日志中包含trace_id，必须优先使用trace_id，不得使用srn、requestId等其他字段
- **常见错误**：不要因为srn在JSON结构中比较显眼就优先使用srn，必须先扫描trace_id字段

## 日志关键字识别

### 识别目标
基于代码分析，识别：
- 代码中使用的日志打印语句
- 日志级别的使用模式
- 关键业务标识符（如用户ID、订单号等）
- 可能的错误处理路径
- 与追踪ID相关的日志拼接逻辑

### 识别方法
1. 查找代码中的logger.info/error/debug语句
2. 识别关键参数（用户ID、订单号、业务标识等）
3. 理解追踪ID在日志中的拼接方式
4. 确定相关的服务名称和模块

# 目录结构

- `SKILL.md`：核心操作原则、入口地址、查询方式与关键字选择资料导航。
- `references/tmux-log-query.md`：本机安装、连接复用、Agent 操作、限量检索与结果核验。
- `templates/jagile-test-runtime-logs.md`：测试环境行云实例实时日志、启动日志和运行时配置核验流程。
- `state_cards.json`：运行时页面状态、可见线索、验证线索和截图引用。
    - `full_frame`：完整浏览器截图，用来看全局页面上下文。
    - `focus_crop`：关键控件、表格行、筛选条件或日志线索的局部截图。
    - `before`：执行变化前的状态，或打开详情页前的状态。
    - `after`：操作或验证后的预期状态。
- `images/`：按流程和状态命名的关键截图。
