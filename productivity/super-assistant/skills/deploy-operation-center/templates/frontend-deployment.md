## 1. 先读取项目规范

优先读取前端仓库中的 `.nvmrc`、`package.json`、锁文件、构建脚本和需求部署文档。记录：Node 版本、包管理器、构建 mode、输出目录、静态资源空间和网页发布入口。

不要为了部署顺手升级依赖、重写锁文件或调整其他页面。只有项目依赖损坏且用户授权时才删除 `node_modules` 后重新安装。

## 2. 公共准备

使用 NVM 时，在同一个 shell 中加载 NVM、切换 Node、安装依赖和构建，避免新终端里再次出现 `node: command not found`。

部署前确认项目属于老项目还是新项目；两者的审批和部署动作相同，但构建命令、制品处理和行云应用可能不同。安装文档指定的 Joyer CLI；全局安装会改变用户环境，执行前应确认当前版本和授权：

```bash
npm install -g joyer-cli@1.4.9-rc.4
```

遇到 504 或无上传/发布权限时，不要反复重试；先确认网页端是否已经生成版本，再按团队约定联系 `liuyuan295` 处理权限。

`dist` 冲突不作为阻塞项，后续构建会重新生成产物。不得因处理 `dist` 冲突覆盖源码或删除测试文件。

## 3. 部署测试环境

新老项目均按以下顺序执行：

1. 在隔离且可审计的工作树中切到 `development`，执行 `git pull origin development`。
2. 执行 `git merge <自己的需求分支>`，只解决真实冲突，不修改 `master`。
3. 完成测试后提交并推送 `development`；测试环境生成的 `dist` 不提交到 `development`。
4. 执行 `npm run build:test`。若命令提示缺少登录态，按提示回车打开浏览器并完成登录，登录成功后等待脚本上传产物。
5. 上传完成后核对目标空间、环境、版本号、创建人和创建时间，再执行网页发布。

JoySpace 原文写有“登录成功但未上传时重新执行 `npm run dev`”。该命令是否包含上传逻辑取决于仓库脚本；必须先检查 `package.json`，不得盲目执行。若项目采用构建、上传分离流程，则使用项目专属上传命令；`new-marketing` 的已验证命令见第 6 节。

## 4. 部署预发环境

预发部署必须先取得用户明确授权。新老项目均先执行：

1. 切到 `pre-development`，执行 `git pull origin pre-development`。
2. 执行 `git merge <自己的需求分支>`。
3. 完成测试后提交并推送 `pre-development`。
4. 按项目类型执行下表中的构建和制品处理。
5. 打开对应行云应用，在 `pre-development` 上触发构建。
6. 构建成功后点击部署预发，选择固定预发，并打开“上传切量”开关。

| 项目类型 | 预发构建命令 | 制品处理 | 行云应用 |
| --- | --- | --- | --- |
| 老项目 | `npm run build:pre2` | 将构建后的 `dist/start` 文件提交到仓库 | `http://jagile.jd.com/jdosCD/ls/CI/old-marketing-system-fe/APP_IMAGE` |
| 新项目 | `npm run build:pre` | JoySpace 原文仅写到“把打包后的 dist”，未说明是否提交；必须回查仓库和项目专属部署文档，不得自行推断 | `http://jagile.jd.com/jdosCD/ls/CI/new-marketing-system-fe2/APP_IMAGE` |

## 5. 部署生产环境

生产部署必须取得用户对本次应用、版本和环境的明确授权，并遵守受保护分支和人工审批规则。不得从“部署前端”或测试环境授权推断可以修改 `master` 或上线生产。

1. 读取项目专属上线文档、`package.json` 和分支保护规则，确认生产构建命令通常为 `npm run build`、输出目录以及 `dist/start` 是否必须入库。
2. 获取最新 `origin/master`，在隔离工作树或需求分支上确认待上线提交完整包含最新主干。默认通过 PR 或团队指定的人工作业合入 `master`，不得直接推送受保护分支。
3. 使用目标发布提交和项目锁定的 Node、包管理器执行生产构建；检查退出码、产物内容、环境变量和接口地址。团队原流程要求生产构建产物提交到 `master` 并由有权限人员合入，但必须以当前项目文档为准，不能把测试包或本地产物直接推上生产分支。
4. 代码及需要入库的产物合并后，打开上表中对应的新/老项目生产应用，在 `master` 上发起构建，并核对构建提交、构建人、制品版本和时间。
5. 构建成功后发起“上线申请”：填写测试审核人和上线审核人，选择关联空间和本次需求卡片，设置流程有效期后提交审批；不得替用户选择未知审批人或需求卡片。
6. 测试和上线审批均通过后进入“实例列表”，选择团队允许的部署入口，使用“滚动部署”并再次核对应用、版本和实例范围。
7. 等待部署完成后按第 8 节验证线上静态资源和关键业务页面；审批完成或平台显示成功都不能替代线上验证。

## 6. 手动构建与 Clear 上传

本需求中 `new-marketing` 已验证过的测试环境示例是：

```bash
nvm use 14
npm install -g joyer-cli@1.4.9-rc.4
npx vue-cli-service build --mode test
```

这只是已验证示例。其他项目或后续版本必须以当前部署文档和 `package.json` 为准。

构建后检查退出码、输出目录和关键资源，确认没有把本地代理或开发环境地址编入测试包。

本需求中曾使用的 Clear 上传示例：

```bash
jr clear from ./dist/ to marketing-equity:test
```

命令出现网关超时不代表上传一定失败。先到网页端确认版本、上传人、时间和文件是否已经生成，再决定是否重试，避免重复产生多个版本。

## 7. 网页发布

静态资源上传与网页“发布/上线”是两个阶段。Git 仓库 `master` 分支权限和 Clear 空间发布权限也是两套权限，不要因为研发没有 master 上线权限就推断不能发布测试环境静态资源。

网页发布前核对：

- 空间和环境与本轮获授权的测试、预发或生产目标完全一致。
- 选择的版本由本轮账号上传。
- 上传时间、资源数和备注匹配。
- 用户已明确授权当前环境发布；生产授权不能由测试或预发授权推断。

## 8. 远端生效验证

不能只看发布状态。至少执行：

1. 打开本轮目标环境的真实 URL，而不是本地站点或其他环境。
2. 强制刷新或使用无缓存请求。
3. 比较远端 JS/CSS 文件哈希、内容特征或构建版本与本地产物。
4. 进入本需求具体页面，验证新增选项、文案或交互。
5. 检查浏览器控制台和关键接口请求。

记录发布版本、账号、时间、测试 URL 和验证结果。若页面仍是旧资源，先检查 CDN/HTML 入口引用和缓存，再重新发布，不要先修改业务代码。
